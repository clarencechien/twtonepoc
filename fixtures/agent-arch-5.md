# 動詞沒變，受詞換了
<!-- imitator /r/agent-arch-5 · 2026-11-09 · 架構筆記 VOL.5 -->

Eskil Steenberg 2023 年那場〈Architecting LARGE software projects〉，講的是怎麼讓一群人做出不會垮的大系統。2026 年，寫程式碼的大半已經是 agent。這一篇把那堂課拆成架構師的七個動詞，上半照原樣整理，下半逐一重譯：哪些動詞做法不變，哪些受詞必須換，哪一個現在只剩人能做。

研究稿 2026-11-09 · 接 VOL.1–4 · 上半依據 Steenberg 的演講（YouTube，約兩小時）與他 2025 年 BSC 的續講。下半為本篇判讀，章節碼前蓋「譯」章 · 引文處皆為轉述，非逐字

## 00 · 轉向：前四篇架構的是給 agent 跑的系統，這篇是由 agent 寫的系統

接回 VOL.1–4 前四篇把 agent 當零件：放進 workflow 的哪個節點，迴圈的上界與退出條件，殼買哪一層，Jev 式分類機該站在 cascade 的哪一格。方向都是「系統裡有 agent」。

這一篇方向反過來。系統本身是人設計的，但大半程式碼由 agent 寫出來。問題從「agent 該放哪」變成「架構師還剩哪些事要自己做」。這個問題 2023 年有人替我們先答過一半，只是當時他對著的是人。

Eskil Steenberg 是一個人寫整套 3D 工具鏈、網路協定與遊戲引擎的獨立開發者。他那場演講沒有投影片，兩小時對著 C 程式碼講怎麼架構大型專案，核心是四個最佳化目標、黑盒子、primitive 與格式設計，配三個虛構案例：影片剪輯軟體、醫療資料系統、噴射戰鬥機的作戰系統。

他講的每一件事，都是為了降低一群人一起做事的成本。2026 年那群人大半換成了 agent，成本結構跟著換。這篇就是在問：同一套動詞，受詞換了之後，哪些照用，哪些要重寫。

怎麼讀：原文 01 到 08 是整理，不加判斷。中間一節樞紐只講「什麼換了」。譯述 01 到 07 與原文同號，每節開頭標對照。想跳著看，兩半同號的章節互相對得上。

## 上半 · 原文 · 2023：AI 之前的架構師，做七件事

### 原文 · 01 · 定目標：四個，而且會互相拉扯

開場他先講這套做法在最佳化什麼。四個目標：可靠（寫完就不用回來修的程式碼）、可擴充（十年後還能加功能而不重寫）、人可以加（加人不會拖慢既有的人）、速度不衰減（第十年寫功能跟第一年一樣快）。

第一條他講得最重。目標是寫「完成」的程式碼：寫完就是對的，之後不用頻繁回來修。這意味著當下要多花一點功夫，他認為值得，理由是第四條。

第四條是整場最反直覺的一句：今天寫五行，比今天寫一行、以後再回來改那一行便宜。一般人覺得少寫是省，他算的是總帳。回來改要重讀上下文，重建當時的理解，再重跑驗證，那些成本遠大於多寫四行。大型專案的速度之所以越做越慢，是因為每個人都在回頭改自己與別人幾年前寫的東西。

這四條會拉扯。可擴充常常與可靠衝突，因為擴充點本身就是不確定性。團隊可擴展與速度衝突，因為人多溝通就多。他後面講的每一個技術手段，都是在調解這四條。

### 原文 · 02 · 選 primitive：整個系統繞著它轉的那個單位

Unix 的 primitive 是檔案。所有工具都操作檔案，所以任何工具都能接任何工具。他認為大系統要先找到自己的那個「檔案」。三個案例的答案都比表面的名詞再退一層：影片剪輯軟體是帶動畫參數的時間軸片段而不是影片，醫療資料系統是醫療事件而不是病歷，噴射戰鬥機是世界的即時狀態而不是感測器讀數。

退那一層的理由每次都一樣。「病歷」只能裝過去；「事件」同時裝得下過去的就診、現在的狀態與未來的預約，而且每一筆長得一樣，所以同一套工具能處理全部。「影片」是輸出；「片段」是剪輯、調色、字幕全部共同操作的對象。「感測器讀數」是來源；「世界狀態」把雷達、油量、武器狀態放進同一張圖，感測器只是這張圖的供應者，飛彈與儀表板只是這張圖的消費者。

選對 primitive 的效果是乘法：工具數乘以資料類型數，變成工具數加一。選錯的代價也是乘法，每個工具都要特別處理例外，而且越晚發現越貴。這是他整場演講裡唯一一個「沒有技術手段可以事後補救」的決定。

### 原文 · 03 · 畫牆：黑盒子、不洩漏的 API、看不懂就重寫

把大專案拆成很多小專案，每個小專案是一個黑盒子，只透過一組穩定、有文件的 API 對外。用的人不需要知道裡面怎麼做，做的人可以隨時把裡面整個換掉。

牆要真的是牆。他舉的反例是資料存取 API 允許傳 SQL 字串進去：那一刻起你永遠綁在 SQL 資料庫上，因為每個呼叫端都知道了牆後面是什麼。好的 API 只暴露語意（我要這個病人的事件），不暴露結構（它存在哪張表）。語意穩定，結構才有自由。

牆的另一面是重寫權。模組夠小、API 夠穩，裡面壞掉或看不懂時就整顆重寫，不要去修。修一個看不懂的東西比重寫一個看得懂的東西慢，而且修完還是看不懂。這條是黑盒子真正的紅利，常被漏掉。

每個模組配一個小測試程式。他講的脈絡是跨平台移植：移植時先讓那個小程式跑起來，問題面積最小、除錯最快。它同時是 API 的活文件，示範這個盒子該怎麼用。

牆上面的任何人都不知道資料存在哪、用什麼存。所以底下可以兩套並行、逐步搬，風險被牆吃掉。

### 原文 · 04 · 包平台：你不擁有的東西，都隔一層

作業系統、繪圖 API、視窗系統、第三方函式庫，任何不是你控制的東西，不要直接呼叫，自己包一層。他特別補了一句：就算那個開源專案很好、很多人用，你還是不控制它。它會改版，會改授權，會停止維護，而你的整個程式碼庫到處都是對它的直接呼叫。

語言選擇是同一條邏輯的延伸。他用 C89 或 C99 的保守子集，理由跟品味無關：幾十年來的編譯器對它的解釋一致，不會在你腳下變。語言是最底層的平台，選一個會動的平台，上面所有的「可靠」都是假的。

包一層的代價是前期多寫程式碼，而且看起來多餘。回報在第四條目標：十年內平台換三次、函式庫棄用兩次，每次你只改那一層。

### 原文 · 05 · 分人：一人一模組，介面先於實作

黑盒子不只是技術切法，它是組織切法。每個模組最好由一個人負責，整顆放得進一個人的腦袋。他沒有引 Brooks，但講的是同一件事：溝通成本隨人數平方成長，模組化的目的就是讓大部分的人不必跟大部分的人講話。

要做到這點，介面要先於實作定下來。先把 API 寫好，各自回去做裡面。噴射機案例把這點推到極端：訂閱與發布的協定甚至可以公開，讓不同承包商各自開發相容的子系統，彼此不必見面。

承包商拿到的只有協定。他們不知道、也不需要知道核心怎麼寫，核心也不需要知道有多少訂閱者。

### 原文 · 06 · 造工具：工具是專案的一部分，不是副產品

噴射機案例的最底層是一整塊「大量開發工具」：模擬器讓你不用真的飛，記錄器把每一次的狀態流存下來，回放器讓錯誤可以重現，fuzzer 對協定亂丟封包。這塊通常被當成有空再做的東西，他把它畫成架構的一層，理由是多承包商的專案沒有這一層就無法協作：誰都沒辦法在自己的桌上驗證自己的那塊。

影片剪輯案例講的是另一種工具：函式庫。核心只管時間軸與片段，MP4 解碼、濾鏡、字幕全部是外掛；而 UI、繪圖、文字排版、平台封裝這些通用的東西抽成可重用的函式庫，下一個專案直接拿去用。

三層裡只有中間那一小塊是這個產品特有的。上面的 launcher 是薄殼，下面兩層是資產。

### 原文 · 07 · 設計格式：軟體設計的本質

他的總結是一句很強的話：軟體設計就是格式設計。API、檔案格式、網路協定、程式語言，全部是格式。設計好一個格式，等於替它兩端的所有實作畫好邊界。六條原則：語意 vs 結構、雙向性、少即是多、易於實作、保持實作自由、先想清楚約束。

這六條放在一起看，有一條共同的性質：它們都是在限制。格式的價值在它不允許什麼，因為每個不允許都替所有實作者省下一段程式碼，也替未來的你省下一段相容性處理。

演講末尾有一張圖，講一個健康專案的程式碼長什麼樣：大量可重用的函式庫，一個精簡的核心，加上用來長功能的外掛。這張圖在原版頁面上掉了，下半的 07 會重畫，而且會多標一件他當年不需要標的事。

### 原文 · 08 · 反方：這是一個人的方法，還是通用的方法

這場演講 2025 年 8 月在 Hacker News 被重新討論時，意見明顯分歧。贊成的人說黑盒子加針孔大小的輸入輸出，是他們碰過最好維護的程式碼。反對的人說他太獨斷，兩條最基本的主張就站不住：所有東西都公開成 API 且不給人看內部，以及一切都切到一人一模組的粒度。有人把它歸因到他的處境：一個人、對 win32 與 OpenGL 有深厚的專業、想單槍匹馬做出厲害的程式。這些條件不是多數團隊有的。有人直接說，除了黑盒子那條，大部分建議不是通用的好建議。

他自己 2025 年在 BSC 的續講也值得放進來。他批評業界把「可維護」當成品質的主要指標，比喻成一輛每天壞但很好修的車，沒人會說那是好車。好的軟體是做完的軟體；做完的軟體才能被抽成函式庫重用。他也承認自己有「不是最近寫的就想重寫」的毛病。另一個他點名的結構性原因是訂閱制：一次性買斷的軟體可以做完，訂閱制逼出無限的重複開發，專案在功能齊全時反而被砍。

反方的核心可以收成一句：這套方法假設每個模組都有一個能力夠也專注夠、不用跟別人商量的人。多數組織供應不了這麼多這樣的人，所以它是獨行俠的方法。這句話留著，下半要回來看它。

## 樞紐：三個換掉的成本

上半每一條建議背後都有一張成本表。2026 年那張表有三格改了數字，其餘沒動。

2023 溝通成本：人跟人講清楚一件事很貴，人數平方成長。所以切模組、所以一人一顆。2026 context 成本：一個 agent 能可靠處理的範圍，是它 context 裝得下、而且裝進去之後還不出錯的範圍。切法的理由從會議室搬到 token。

2023 寫與改：寫五行比以後改一行便宜，因為改要重讀，重建理解，重驗證。2026 寫趨近零，讀懂沒變。產生一段程式碼幾乎免費；確認它對、看懂它為什麼對，還是要人或要測試。貴的那端換邊了。

2023 牆由誰守：黑盒子的邊界由編譯器與連結器守。你看不到的符號，你就呼叫不到。2026 牆由 prompt 守：agent 看得到整個 repo，「不要動其他模組」只是一句話。牆要重新變成實體，否則它不存在。

其餘沒變的成本：選錯 primitive 的代價仍是全系統，格式每多一個功能仍是兩端都要實作，平台仍會在你腳下變，而且變得更快。下半的七節就是把這三格新數字代回去重算。

## 下半 · 譯述 · 2026：AI 時代的架構師，還是七件事

### 譯述 · 01 · 定目標：同樣四個，排序換了

四個目標都還在，但重要性重排。可靠排第一，比 2023 年更前面。理由是「寫完就不用回來」的價值變高了：回來的成本現在是重讀一段你沒寫過的程式碼。2023 年回頭改的是自己或同事幾年前的東西，至少有人腦裡留著一點脈絡。2026 年回頭改的是某個 agent 在某個 session 產出的東西，脈絡隨 session 結束就蒸發。

速度那條要重算。「今天寫五行好過以後改一行」在 2026 年幾乎是恆真式，因為寫五行跟寫一行的成本一樣接近零。差別全部落在「以後有沒有人要讀它」。所以這條建議的 2026 版是：讓 agent 一次寫完整，連測試與文件一起寫，不要為了省 token 讓它寫一個以後要補的骨架。省下的 token 比起以後重讀的人工，不是同一個數量級。

可擴充那條有陷阱。agent 加功能的邊際成本接近零，所以「可擴充」會自己發生，而且過頭。原文 07 說格式每多一個功能兩端都要付，這句話 2026 年反而更重要，因為付錢的一端（實作）變便宜了，另一端（所有要理解這個格式的人與 agent）沒有。這留到譯述 07。

團隊可擴展那條，受詞整個換掉，留到譯述 05。

### 譯述 · 02 · 選 primitive：唯一沒變便宜的決定，也不該外包

七個動詞裡，這一個 2026 年最沒變，而且是刻意不能讓它變。三個理由。

第一，agent 選 primitive 的方式是外推。它看到現有的資料表叫 patient_record，就會繞著「病歷」設計；看到輸入是 mp4，就會繞著「影片」設計。退一層到「事件」或「片段」需要知道這個系統五年後會長什麼樣，那不在任何 repo 裡。

第二，選錯的代價仍是全系統，而且更隱蔽。2023 年選錯 primitive，每個工程師都會在自己的模組裡碰到例外，會抱怨，會把問題帶到會議上。2026 年每個 agent 都會安靜地在自己的模組裡處理掉那個例外，寫一段特殊情況的程式碼，然後測試過了。接回 VOL.1 它們不會報錯，它們會成功。primitive 選錯這件事會被三十段各自正確的特殊處理蓋住，等到你發現時已經沒有一個模組是乾淨的。

第三，這是人唯一握有資訊優勢的決定。agent 知道的是 repo 裡有什麼；primitive 要回答的是「這個系統要服務的世界，最小的穩定單位是什麼」，那是領域知識加上對未來的賭注。

做法是把 primitive 寫進每個 agent 都會讀的那份文件裡，而且要同時寫「它是什麼」與「它不是什麼」：核心單位是事件，病歷只是事件的一種檢視。少了「不是什麼」那半句，agent 會自己補一個更順手的。

### 譯述 · 03 · 畫牆：重寫權變成日常，牆要變成實體

黑盒子在 2026 年有一條紅利直接兌現：看不懂就重寫。給 API、給測試，讓 agent 重寫一整顆模組的成本，已經接近他當年的理想。一個 context 裝得下一顆黑盒子，這件事就成立；裝不下，這顆盒子本來就太大。所以黑盒子的大小有了一把新的尺。

但重寫權有一個前提，2023 年隱含、2026 年要寫明白：API 真的穩，而且測試是牆的一部分。agent 重寫一顆模組時，唯一告訴它「你做對了」的東西是 API 的型別與那組測試。接回 VOL.1 測試就是這顆黑盒子的 oracle。沒有 oracle 的重寫，只是換一組不知道對不對的程式碼。原文 03 那個「每個模組配一個小測試程式」，2026 年升級成每個模組的驗收條件，而且在派工之前就要存在。

牆本身要重新變成實體。2023 年牆由編譯器守：符號不公開，你就呼叫不到。2026 年 agent 看得到整個 repo，牆只剩文件裡的一句「不要動其他模組」。這句話在它卡關、測試不過，而隔壁模組裡剛好有一個可以改的函式時，會被繞過。接回 VOL.3 這是 harness 的事，不是 prompt 的事：目錄層級的寫入權限、import 規則的 lint、CI 擋下跨模組的 diff。原文 03 說 API 是一道牆保護後面的實作可以自由替換；2026 年要加一句，牆要有東西守，否則它只是一條畫在地上的線。

### 譯述 · 04 · 包平台：多了一個最該包的對象

原文 04 的清單 2026 年多了一項，而且排第一：模型供應商。它符合「你不擁有的東西」的每一個特徵，而且程度都比作業系統與開源函式庫嚴重。版本以月計 deprecate，同一個 API 呼叫的行為會隨模型更新而漂，計價方式會改，速率限制會改。它是目前所有平台層裡最不 dependable 的一層，也是最常被直接 import 進業務邏輯的一層。

包法跟他講的一樣，只是多一件事。一層薄的 adapter 隔開供應商 SDK，讓模型可換，這是原文的做法；多出來的是錢包保險絲。接回 VOL.3 迴圈上限與成本上限，每次呼叫的 token 與費用落檔，這些在 2023 年的平台層不存在，因為作業系統不會因為你多呼叫幾次就多收錢。

要包的還有 agent 的殼本身。VOL.3 講過三條鎖定軸：模型、平台、狀態存放。用他的話重說一次就是，harness 也是你不擁有的東西，狀態與流程不要住在它裡面。

語言選擇那條，2026 年出現一個 2023 年沒有的變數：模型對這個語言的熟悉度。C89 的理由是穩，但模型在一個冷門穩定的語言上寫出來的程式碼品質，可能遠低於在一個主流但會動的語言上。這是一個真的取捨，沒有乾淨的答案。保守的解法是取交集：主流語言裡最穩定的子集，不追新語法，不用邊緣功能。穩定與熟悉度在交集裡都還夠。

### 譯述 · 05 · 分人：一人一模組，變成一個 context 一模組

這一節受詞整個換掉，但結論幾乎原封不動。「一人一模組」的理由是溝通成本；「一個 context 一模組」的理由是 context 成本。兩者都在說同一件事：負責一顆模組的那個單位，要能把整顆裝進去，而且不用跟別的單位商量就能完成。

介面先於實作，2026 年從建議變成必要條件。你不能對 agent 說「先做做看，介面之後再談」，因為它會做完，而且介面會是它順手定的那個。派工之前先有型別與 API 簽名，先有驗收測試，這就是原文 05 的「先把 API 寫好，各自回去做裡面」，只是「各自」現在包括非人。

多 agent 的正確模型是噴射機案例的承包商，不是會議室。接回 VOL.3 子代理各自拿乾淨的 context，對著一組公開的 API 做自己那塊，回傳給父代理的只有摘要。承包商不開會，他們拿到協定文件就回去做；他們交付的也不是過程，是通過驗收的東西。orchestrator 與 worker 的分工要照這個樣子，不要照一群人在白板前討論的樣子。

現在回頭看原文 08 那句反方：這套方法假設每顆模組都有一個能力夠也專注夠、不用商量的人，多數組織供應不了。2026 年這個假設反過來成立了。每個 agent 都是一個對某層技術有深厚訓練，對你們的領域沒有任何認識，而且不會主動找人商量的獨行俠。他的方法從「只有少數團隊做得到」，變成多數團隊的預設條件。HN 說他的處境特殊，這個處境現在可以用 API 呼叫出來。

### 譯述 · 06 · 造工具：整塊變便宜，所以要小心它變大

原文 06 那一整層「大量開發工具」是 2026 年收益最大的地方。模擬器、記錄器、回放器、fuzzer 有三個共同特徵：規格明確、有 oracle（它模擬的東西本身就是標準答案）、用完可以丟。接回 VOL.2 這正好是 CELL C 的形狀，agent loop 的主場。2023 年這層常被跳過，因為沒有人力。2026 年它應該是第一批寫出來的東西。

黏合程式碼同理。原文 03 那套新舊系統並行、逐步轉移的策略，最貴的部分是中間那層黏合，它瑣碎而且一次性，每個欄位都有例外。這正是最適合交給 agent 的程式碼，所以遷移的成本結構變了：牆兩邊的系統仍要人設計，牆本身的黏合幾乎免費。他當年說黏合程式碼大幅降低風險，現在它也大幅降低成本。

便宜有一個副作用。工具變成零成本之後，工具會長成第二個系統：每個 agent 替自己寫一個 helper，三個月後有五個不相容的模擬器、四套記錄格式。原文 03 對模組的要求要原樣套在工具上：工具也是黑盒子，也有 API，也只有一份。通用函式庫那一層（UI、繪圖、檔案）的 2026 版同樣如此：讓 agent 寫，但只寫一次，而且寫進共用層。

### 譯述 · 07 · 設計格式：人留下來的那塊

六條格式原則每一條 2026 年都成立，而且都更強。理由是同一個：格式是限制，而 agent 在沒有限制的地方會把所有可能性都做出來。

「少即是多：做出選擇」在 2023 年是對人的紀律要求，因為人會想兩個都支援。2026 年 agent 不會「想」兩個都支援，它會直接兩個都支援，因為對它來說成本一樣。多邊形與 NURBS 二選一，這個「選」的動作只有人會做。「雙向性」同理：加一個欄位的實作成本趨近零，但每個要讀這個格式的人與 agent 都要多處理一個欄位，而且永遠。格式膨脹從一種風險變成預設方向，格式設計從一個專業變成一種剎車。

「保持實作自由」在 2026 年直接變現。原文說 API 不洩漏實作，牆後面才能自由替換。譯述 03 說替換現在幾乎免費。兩句合起來就是：你能不能讓 agent 重寫一顆黑盒子，完全取決於當年格式有沒有洩漏。格式設計好的系統，每一顆模組都能被重生，設計不好的，每一顆都被它的呼叫端釘死。

所以這七個動詞走到最後，剩下的那塊是：選 primitive、畫牆（決定 API 的語意）、設計格式。它們是同一件事的三個名字，都是在決定「這個系統裡什麼不允許」。寫程式碼的那部分幾乎全部可以交出去，決定不允許什麼的那部分交不出去。

他當年畫這張圖是要說核心應該很小。2026 年要多說一句：核心旁邊還有一塊更小的，叫格式，它不是程式碼，而且不能交出去。

## 09 · 規則與反模式

RULE 07 · 不外包的三件事：primitive、API 語意、格式，由人決定，寫進每個 agent 都會讀的文件，而且寫明「不是什麼」。這三件是同一個決定：這個系統裡什麼不允許。寫程式碼可以交出去，決定不允許什麼不能。

RULE 08 · 牆要有東西守：模組邊界要由 harness 實作：寫入權限與 import 規則，CI 擋跨模組 diff。prompt 裡的一句話不是牆。接 VOL.3 的殼：殼不決定對錯，它決定錯了多貴；跨模組伸手就是它該讓它變貴的那種錯。

AP-21 · 跨模組伸手：agent 為了讓自己的測試過，改了隔壁模組的程式碼。它不是惡意，是最短路徑。防守在 RULE 08，不在 prompt。

AP-22 · 裸 import 模型 SDK：供應商 SDK 直接出現在業務邏輯裡，沒有 adapter、沒有保險絲。原文 04 的 2026 年版：它是你最不擁有的平台層。

AP-23 · 把生成速度當開發速度：以產出行數或功能數衡量進度，忽略每一行以後都要有人讀懂。速度那條目標的真正量尺，是第十年加功能跟第一年一樣快，不是這週產出多少。

AP-24 · 讓 agent 選 primitive：第一個 session 就讓 agent 從現有 schema 起草資料模型，然後所有模組繞著它長。它會選表面的名詞。選錯之後每顆模組都會安靜地處理掉例外，沒有一處報錯。

他 2023 年對著人講的每一條，2026 年都還成立。差別是當年需要紀律才做得到的事，現在有一半由成本結構自動實現，另一半變成只有人能做。

這也是 VOL.5 在這個系列裡的位置。前四篇在問 agent 該放在系統的哪裡。這篇在問，當 agent 寫了大半個系統，架構師站在哪裡。答案是那三個不外包的動詞，以及一道有東西守的牆。
